\section{System Architecture and Conceptual Design}

\begin{figure}[!htbp]
	\centering
	\includegraphics[width=1\textwidth]{concep_diagram.png}
	\caption{Proposed Conceptual Diagram}
	\label{fig:Description and Methodology}
\end{figure}

The system follows a layered architecture with a focus on modularity, scalability, and reliability. The conceptual framework (Figure~\ref{fig:Description and Methodology}) integrates the following:

\begin{itemize}
    \item \textbf{Vehicle Sensing Subsystem:} Digitally calibrated fuel-level sensors, GPS modules, and driver rest-time monitors. Sensor signals are collected via ECU or OBD-II ports.
    \item \textbf{Edge Processing:} The MCU performs signal preprocessing, filtering, smoothing, synchronization, and timestamping before transmission.
    \item \textbf{IoT Communication:} LoRa transceivers enable low-power, long-range data transmission; GSM acts as a backup channel for essential alerts, balancing cost and bandwidth considerations.
    \item \textbf{Cloud Intelligence:} Historical data is used to train unsupervised ML models (Isolation Forest, Matrix Profile) to detect anomalies. The cloud evaluates incoming real-time data and triggers alerts.
    \item \textbf{Client Visualization:} A web-based dashboard provides real-time visualization of fuel levels, routes, alerts, and historical playback for decision-making.
\end{itemize}

\begin{figure}[!htbp]
    \centering
        \includegraphics[width=0.8\textwidth]{concep_archi.png}
    \caption{Proposed System Architecture Diagram}
    \label{fig:system_architecture}
\end{figure}

The system architecture (Figure~\ref{fig:system_architecture}) follows a layered, end-to-end IoT design composed of three major layers: the data acquisition layer, the communication and cloud processing layer, and the data visualization layer. This structure supports real-time fuel monitoring, GPS-based route tracking, driver safety alerts, and cloud-based anomaly detection.

At the data acquisition layer, the vehicle is outfitted with digitally calibrated float sensors integrated through the truck’s ECU/diagnostic connector to obtain accurate fuel-level measurements. The microcontroller (MCU) serves as the primary edge device, interfacing with the float sensor, GPS module (logging coordinates at 5-second intervals), rest alert subsystem, and time-tracking module. A LoRa transceiver functions as the main channel for transmitting fuel, location, and operating-hour data to the cloud, while a GSM module is used strictly as a fallback communication interface, activated only when LoRa connectivity is unavailable and limited to essential alerts due to bandwidth and cost constraints.

The communication and cloud processing layer handles real-time data ingestion and anomaly detection. Incoming packets from the vehicle are received through cloud-based API endpoints and routed to processing services where the trained machine learning model—developed offline using Matrix Profile or Isolation Forest—is deployed for fuel anomaly evaluation. A Python-based alert engine evaluates fuel–location–time patterns and generates automated rest reminders, maintenance notifications, and anomaly flags. All validated data and event logs are stored in a centralized cloud database for long-term analysis.

The data visualization layer consists of a web-based monitoring dashboard that retrieves information from the cloud database. Through this interface, clients can view real-time truck locations, fuel levels, distance traveled, driver operating hours, and alert notifications. The dashboard also supports historical playback of route and fuel usage trends, enabling improved operational awareness and proactive decision-making.

Overall, the architecture highlights the complete data flow—from ECU-integrated sensing and MCU preprocessing, to LoRa/GSM communication, to cloud-based machine learning and dashboard visualization—demonstrating a scalable and modular IoT system for fleet monitoring and anomaly detection.



\section{Implementation}

\label{sec:implement}

\subsection{Data Acquisition and Preprocessing}

Data acquisition and preprocessing are crucial for reliable anomaly detection. The methodology includes:

\begin{enumerate}
    \item \textbf{Sensor Calibration:} Fuel-level sensors are calibrated using known volumes, verified with manual measurements, and cross-checked with historical data trends.
    \item \textbf{Signal Filtering:} Raw sensor signals are filtered using moving-average and median filters to reduce noise caused by vehicle motion or fuel sloshing.
    \item \textbf{Synchronization:} Fuel, GPS, and operating-hour data are timestamped and synchronized to ensure consistent data alignment for model evaluation.
    \item \textbf{Feature Engineering:} Derived features include fuel consumption rate, distance-to-fuel ratio, route segment performance, and driver behavior metrics, which feed into anomaly detection models.
\end{enumerate}

\subsubsection*{Study Procedures}

Upon voluntary agreement to participate, the study procedures will be conducted as follows:

\begin{enumerate}
    \item Before the trip begins, a member of the research team will install a monitoring device or IoT module unit in the truck assigned to the participant.
    \item Once installed, the device will automatically record fuel-level readings at regular intervals, distance and travel time, and GPS location data during normal vehicle operations.
    \item For randomly selected trips, participants may be asked to perform a supervised task simulating fuel draining from the tank. This procedure will be conducted to test the accuracy of the prototype's anomaly detection function.
    \item Participants will not be required to change their normal driving behavior during the data collection period.
    \item After the data collection period is completed, a member of the research team will remove the monitoring device from the vehicle.
    \item The study will also conduct a survey with the fleet administrator to gather feedback on the device's functionality and any problems encountered during its use. The survey will not be administered to the drivers and will not include personal questions directed at them.
\end{enumerate}

\subsection{System Methodology}
The system was implemented as follows:

\begin{itemize}
    \item \textbf{MCU and Edge Layer:} ESP32/NodeMCU microcontrollers for filtering, timestamping, and initial anomaly scoring.
    \item \textbf{Vehicle Interfaces:} CAN bus or OBD-II for fuel-level readings; GPS module for location and speed tracking.
    \item \textbf{Communication Layer:} LoRa transceivers for real-time cloud updates; GSM backup for critical alerts.
    \item \textbf{Cloud Layer:} Python-based ML models for anomaly detection deployed on cloud servers; REST APIs for data ingestion; PostgreSQL/NoSQL database for structured storage.
    \item \textbf{Visualization Layer:} Web dashboard for real-time monitoring, historical trend analysis, and alert management.
\end{itemize}

\subsection{Anomaly Detection and ML Methodology}

The anomaly detection workflow is as follows:

\begin{enumerate}
    \item \textbf{Offline Model Training:} Historical datasets are used to train Isolation Forest and Matrix Profile models to detect abnormal fuel usage patterns.
    \item \textbf{Context-Aware Thresholding:} Thresholds are dynamically adjusted based on vehicle type, route segment, and driver behavior to reduce false positives.
    \item \textbf{Evaluation Metrics:} Precision, FPR, accuracy, and detection latency are calculated; confusion matrices, ROC, and PR curves visualize performance.
\end{enumerate}

\subsection{IPO Chart and Design Pipeline}

The data design  outlines a cohesive pipeline which integrates sensor acquisition, synchronization, cloud transmission, and model-based analysis to enable real-time anomaly detection in fleet fuel systems. Data collection begins with embedded sensors capturing raw signals such as fuel level, fuel flow, GPS coordinates, and ignition events. These signals are preprocessed using filters and signal conditioning circuits to reduce noise and ensure clean input for analysis.

To ensure temporal alignment, all sensor outputs are timestamped and resampled onto a uniform time grid using linear interpolation. This synchronization step is critical for comparing trends across sensor modalities and detecting correlated anomalies. The processed signals are then uploaded to a cloud-based platform for storage and remote access.

For anomaly detection, the synchronized time-series data are used to train and evaluate unsupervised models such as Isolation Forest and Matrix Profile. These models are tested on a dataset composed of real-world and simulated scenarios to reflect both normal and anomalous behavior. Key performance metrics (including MAPE, timestamp drift, detection latency, precision, and false positive rate) are used to assess system effectiveness. This pipeline supports scalable, automated monitoring while laying the groundwork for further model refinement in future stages.

Anomaly detection is carried out in the cloud using machine learning models, including Matrix Profile (STUMPY) for time-series discord identification and Isolation Forest for feature-based outlier detection. Model validation and evaluation are performed using labeled and test datasets, calculating performance metrics such as precision, false positive rate (FPR), detection latency, and overall accuracy.

The system outputs include fuel anomaly flags, such as potential theft or leakage, and driver rest alerts based on cumulative distance or driving duration. Additionally, it provides real-time GPS tracking on a web dashboard, estimated fuel levels as a percentage of tank capacity, and quantitative performance metrics for operational evaluation. This end-to-end flow ensures accurate, real-time monitoring, proactive safety notifications, and actionable insights for fleet management.

\section{Evaluation}
\label{sec:evaluate}

To evaluate these models, the outputs are validated against manually labeled ground truth data. From this, the number of true positives (TP), false positives (FP), true negatives (TN), and false negatives (FN) are counted. Key metrics are computed as follows:

\textbf{Precision}  
\begin{equation}
\mathrm{Precision} = \frac{\gls{not:TP}}{\gls{not:TP} + \gls{not:FP}}
\label{eq:precision}
\end{equation}

Precision reflects how many detected anomalies are truly anomalous. A high precision means fewer false alarms, which is important for maintaining trust in the alerting system.

\textbf{False Positive Rate (FPR)}
\begin{equation}
\mathrm{FPR} = \frac{\gls{not:FP}}{\gls{not:FP} + \gls{not:TN}}
\label{eq:fpr}
\end{equation}

FPR quantifies the likelihood of incorrectly classifying normal behavior as anomalous. Lower FPR values are desired to reduce noise in the system's alerts.

\textbf{Accuracy}
\textbf{Accuracy}  
\begin{equation}
\mathrm{Accuracy} = \frac{\gls{not:TP} + \gls{not:TN}}{\gls{not:TP} + \gls{not:TN} + \gls{not:FP} + \gls{not:FN}}
\label{eq:accuracy}
\end{equation}

Accuracy provides an overall view of model correctness but can be misleading in imbalanced datasets, which is why it's used alongside precision and FPR.

All these metrics use the following classification outcomes:
\begin{align*}
\text{TP (True Positives)} &= \text{Number of correctly identified anomalies}, \\
\text{FP (False Positives)} &= \text{Number of normal events incorrectly flagged as anomalies}, \\
\text{TN (True Negatives)} &= \text{Number of correctly identified normal cases}, \\
\text{FN (False Negatives)} &= \text{Anomalies that were missed by the model}.
\end{align*}

\textbf{Detection Latency}

\begin{equation}
\gls{not:L}_{\mathrm{det}} = \gls{not:Tdetected} - \gls{not:Tactual}
\label{eq:latency-detection}
\end{equation}

where:
\begin{align*}
T_{\text{detected}} &= \text{the time the anomaly truly occurred}, \\
T_{\text{actual}} &= \text{the time it was identified by the system}.
\end{align*}

The objective is achieved if the unsupervised system attains at least 90\% precision (indicating that the majority of flagged events are correct), a false positive rate not exceeding 10\%, and average detection latency under 10 seconds. For interpretability, confusion matrices and performance plots such as ROC and PR curves will be used. Detection events will also be overlaid on synchronized GPS location maps and fuel-level graphs for context-aware validation.
